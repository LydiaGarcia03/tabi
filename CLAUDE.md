# Tabi (旅)

Personal trip-planning web app. Built first for a trip to Japan in 2028 (Tokyo, Kyoto, Osaka), but designed for any destination.

Owner: referred to as **User** (never by name, in any project file). She lives in Brazil and speaks Portuguese; **talk to her in Portuguese (pt-BR)**, but keep everything in the project in **English**: code, identifiers, file names, comments, commit messages, UI text, docs.

## Goal

Something like Wanderlog, plus precise route planning between places:

- Plan each day of a trip as an ordered list of places (pins) shown on a Google map.
- Attach notes to each place: historical context, tickets to have at hand, opening hours, tips.
- Between two consecutive places (A → B), define **exactly how to get there**, as a chain of segments with a transport mode each — e.g. "walk 400 m to X street, then bus line 7 from stop Y to B". Either draw it manually or ask the app for a suggested route.
- Track costs (places, transport, lodging, other) with totals per day and per trip.
- Use everything **offline** on the phone during the trip.
- Usable on her phone (installed as a PWA) and on her PC.

## Hard constraints

1. **Zero cost.** User cannot pay for anything. Only free tiers, and every paid service must be capped so it can never charge. Do not add any dependency, service or API that could bill her.
2. **No scraping.** Never scrape or bulk-extract Google Maps data (violates Google's terms). Use official APIs or open data only.
3. **Static hosting only** (GitHub Pages). No backend server. All data lives on the device (optionally also synced to the user's own Google Drive, see Sync).
4. **No secrets in the repo.** The repo is public.
5. **English everywhere** in the project (see above).

### Transit routing: NAVITIME (decided in Phase 1)
- **Phase 1 result (2026-10-20):** Google's Routes API returns **no routes** for `TRANSIT` in Japan (Shinjuku Station → Senso-ji: empty `routes`, no fallback). NAVITIME returned 3 complete routes with lines, times, fares and track shapes. So NAVITIME is the transit engine; Google is used for maps, places and walking segments.
- NAVITIME Basic plan findings:
  - The `lang` parameter is rejected (`400 bad usage on this contract : Multilingual`), so station/line names come back in Japanese.
  - `shape=true` is allowed: the route geometry (GeoJSON) comes in the same `route_transit` response, so one route costs one request (no separate `shape_transit` call).
  - A `403 You are not subscribed to this API` with an active plan means the key belongs to a different RapidAPI app than the subscribed one.
  - JR fares spanning several JR lines are charged on the last JR segment; earlier JR segments show ¥0.
- **Japanese → English names:** NAVITIME names are Japanese, and machine translation mangles proper nouns (新宿 → "New Lodging"). So names are looked up in a dictionary of official English names of stations, lines and operators built from **Wikidata** (CC0): `scripts/update-japanese-names.mjs` (`npm run names:update`, run manually, output committed in `src/data/japanese-names.json`), used by `src/i18n/japaneseNames.ts`. Homonym stations (e.g. 神田 = Kanda in Tokyo, Kouda in Saga) are resolved by nearest coordinates. Unknown names stay in Japanese; the original Japanese is always shown next to the English (useful to match signs). Works offline, no API.
- **NAVITIME Route (totalnavi)** via RapidAPI — Japanese provider, door-to-door routes by public transport + walking, with fares. Endpoints: `route_transit`, `shape_transit` (polyline to draw on the map), `fare_table`, `fare_comparison`. Note: train times are NAVITIME's estimates, not real timetables — fine for advance planning.
- RapidAPI plan: **BASIC — $0/month, 500 requests/month with Hard Limit** (blocked, never billed, when exceeded), 50 requests/minute. Includes 10,240 MB/month of bandwidth (overage would be $0.001/MB, unreachable: 500 responses of tens of KB ≈ 25 MB). Never switch to Pro/Ultra (Ultra bills overage). Because the quota is small, always store fetched routes locally and never call NAVITIME automatically (only on an explicit user action).
- The RapidAPI website (marketplace/dashboard) is often down with 502/504 errors. That is not necessarily the API gateway itself, but treat the provider as unreliable: hide every route provider (Google, NAVITIME, future ones) behind one `RouteProvider` interface in its own module, handle errors and timeouts gracefully, and never block the user — manual segment entry must always work and saved routes must always be readable.
- RapidAPI host header: `X-RapidAPI-Host: navitime-route-totalnavi.p.rapidapi.com` (base URL `https://navitime-route-totalnavi.p.rapidapi.com`). Not a secret; can live in code.
- The RapidAPI key is **not** committed or baked into the build: the user enters it in the app's Settings and it is stored on the device (and in her Google Drive when sync is on, see Sync). (Baking it in via a GitHub secret was considered and rejected: the build is public and RapidAPI keys can't be restricted by referrer, so anyone could burn the quota, and any paid API later added to the same RapidAPI app could bill.) To move it to another device, the trip backup can carry it: opt-in checkbox "Include my NAVITIME key" on export (`settings.rapidApiKey` in the JSON); importing such a file saves the key on the device once the import completes.
- **Outside Japan, transit suggestions come from Google** (User's decision, 2026-10-28): "Get a suggested route: Transit" asks NAVITIME when the leg starts in Japan (`inJapan`, latitude bands in `src/data/countries.ts` that leave out Korea, Vladivostok, Shanghai and Taiwan) and Google Routes (`googleProvider.computeTransit`, 1 request, region = the trip's first country) elsewhere. The time typed ("Leave at 09:00") is local to the place: `utcOffsetAt` picks, among the trip's countries' time zones (`COUNTRY_ZONES`, summer time from Intl), the one closest to the longitude (Japan + USA: Los Angeles in California); without countries, the longitude alone. Google's `RAIL`/`HEAVY_RAIL` are trains (only `HIGH_SPEED_TRAIN` is shinkansen).
- **Suggestions row** (User, 2026-10-28): "Get a suggested route: [Car] [Public transport] [Walking]" — in Japan "[Car] [Route by NAVITIME] [Walking]". Car = 1 Google Routes DRIVING request without live traffic (`computeDrivingRoute`, Essentials), saved as one `car` segment (a segment mode of its own, pink `#db2777`, cost per car like a taxi, "Follow streets" by driving). Google sends an empty currency when it doesn't know a fare: no fare is saved then, and `formatMoney` never throws on a bad code. A paid ride without a price says "fare unknown (edit the step to add it)" in the timeline and "fare unknown" / "+ fare unknown" in the leg header (`fareUnknown` in `format.ts`; walks, cars and flights from the itinerary excluded).
- Rejected: building our own router from open GTFS data (ODPT etc.) — coverage is patchy (JR and several private lines missing or restricted), too much work. Open data may still be used later just to draw lines/stations.
- Rejected: Ekispert API (free plan has no route search).
- Rejected: in-app AI route suggestions (would need a paid API). User can ask Claude during development/planning instead.

### Offline: the app itself + Organic Maps
Google Maps (app or API) does not provide transit/walking directions offline, and can't import a custom multi-modal route.

- The PWA caches the app shell and keeps all trip data in IndexedDB, so itineraries, notes, segments and costs are readable offline.
- Export each trip/day to **KML** (and GPX) for **Organic Maps** (free, OpenStreetMap-based, excellent offline; imports KML/GPX with pins and tracks). OSM data is good in big Japanese cities; weaker on business info, which is why planning stays on Google.
- Each place and leg also has an "Open in Google Maps" deep link for when there is connectivity.
- KML export also works for Google My Maps if ever wanted.
- **In-app offline map (Phase 10):** a "Use offline map" button on the day page swaps the Google map for a MapLibre map drawn from OpenStreetMap vector tiles downloaded from **OpenFreeMap** (free, no key; stored in IndexedDB, never Google tiles). OpenFreeMap's terms allow offline downloads of ≤ 3,000 tiles or 50 MB each with ≤ 4 parallel requests and a unique User-Agent — a browser can't set the User-Agent (the Origin header identifies the app); the other limits are enforced in `src/offlineMap/`. Protomaps builds were checked first but send no CORS headers (can't be read from the browser).
- **Google terms and the offline map — User's decision (2026-10-21):** Google's terms forbid showing Google Maps content on a non-Google map. To limit it, each Google place is first looked up in the downloaded OSM data (same name within 300 m, `src/offlineMap/match.ts`) and shown at OSM's position; places not found are shown at Google's position anyway (dashed pin), a risk User accepted. Drawn segments (including Google walking routes) are shown too. The KML export to Organic Maps has the same issue.

### The itinerary, and the "Booked" check (business rule, User's decision 2026-10-27)
The trip is planned long before it happens, so **choosing something is not booking it**.

- **Options** = everything being considered. **Ticking ✓ on any option = "I'll use this"**: it goes into the **itinerary** (restaurants/places/shops into a day; hotels and transport into the trip as a stay / journey with dates and price). It does **not** mean it was reserved in real life. In the UI this is always "in the itinerary" ("In the itinerary", "Add to itinerary"), the term the app already used; never "plan" / "planned".
- **"Booked" is not a second state or stage** (User corrected this, 2026-10-27): it is just a check on the item, like "Ticket needed" / "Reservation needed", saying it is reserved in real life. Ticked by User (on the item, or in the checklist, the same flag); off by default. Same word everywhere: "Booked". Places already work this way (`Place.bookAhead` + `Place.booked`); hotels and transport get the same pair.
- **Needs booking** (the other check): hotels and flights always. Other transport only when "Booking needed" is ticked (on by default for shinkansen; off for bus, train, ferry, car). Restaurants "Reservation needed", places "Ticket needed", as before.
- **The checklist lists what needs booking and isn't Booked yet**: hotels and flights in the itinerary, transport with "Booking needed", restaurants/places needing a reservation/ticket. Derived from the itinerary (taking something out of it removes its item); ticking an item = ticking its "Booked".

## Code organization (cleaned up 2026-10-27, User's request)

- **Phone vs computer:** one component for both; the layout differs in CSS (`@media`). JavaScript decides only where the structure really changes (Options' map drawer vs side list, the Logbook's two columns, the Options phone bar), through `useMediaQuery` with the constants of `src/breakpoints.ts`.
- **Screen sizes:** only these widths in `@media` rules (listed at the top of `src/index.css`; `src/breakpoints.ts` has the same numbers): small phones `max-width: 480px`; phones `max-width: 599px` / `min-width: 600px`; wide screens `min-width: 900px` / `max-width: 899px`; the trip sidebar `min-width: 1100px` / `max-width: 1099px`. Don't add other values.
- **Styles:** `src/index.css` is only its header and `@import`s of `src/styles/*.css`, by area and in order (later rules win over earlier ones of the same weight, so the order matters): base (tokens, dark mode, reset), ui (type, shell, forms, buttons, layout helpers), trips, day, offline-map, trip (layout, overview, cities, checklist), options, budget (with the day's money), logbook, options-details (journeys, photos, details), planning (transport, hours), expenses-settings, baggage, sheet, phones-print. New rules go in their area's file.
- **Components:** pages (`src/pages/`) keep state and layout; their parts live in `src/components/` (grouped in a folder when a page has many: `components/options/` — OptionGroup, ChoosePanel, CityFilter, Weights, `itinerary.ts`; `components/logbook/` — DayPicker, StopCard, WideDay). A component file exports only components (Vite's fast refresh; lint warns otherwise): plain functions go in a `.ts` file.
- **Dropdowns:** the app's own (DaySelect, the Logbook's DayPicker, CityFilter, CategorySelect, OptionPicker) and InfoTip close on a tap elsewhere with `useDismiss(ref, open, setOpen)` (`src/useDismiss.ts`); a day's city for them is `dayCity` (`src/db/stays.ts`, a day trip's city alone).

## Scripts (`scripts/`)

Run by hand when needed, never by the build or the deploy; their output is committed.

- `npm run names:update` (`scripts/update-japanese-names.mjs`): downloads from Wikidata the official English names of Japanese stations, lines and operators into `src/data/japanese-names.json` (the dictionary that turns NAVITIME's 新宿 into "Shinjuku", offline, no API). Run it now and then to pick up new stations/lines, then commit the JSON.
- `npm run holidays:update` (`scripts/update-holidays.mjs`): regenerates `public/holidays/<CC>.json` (public holidays, national and regional, this year + 6) from the date-holidays devDependency. Run it once a year to move the range forward, then commit the files.
- `npm run icons` (`scripts/generate-icons.mjs`): generates the app's PNG icons (the torii on the app red) into `public/`. Only needed when the icon changes.
- The README screenshot scripts (demo trip builder + Chromium driver, see Working agreements) are not in the repo: they were throwaway files in a session scratchpad.

No page zoom (`user-scalable=no` in `index.html`, User 2026-10-28: pinching cut components); the maps zoom with their own gestures. Without zoom nothing may be wider than the screen, also with Android's bigger font sizes (User's Galaxy S20 FE cut the day page): every `display: grid` column holding page content is `minmax(0, 1fr)` (an `auto` column grows to its widest unbreakable line), inputs in flex rows get `min-width: 0`, rows of controls wrap. Checked on 2026-10-28 by a throwaway audit (headless Chromium, the demo trip, 17 pages and opened states — leg, place editor, trip tabs, option form, sheets — at 360/375/393/412 px with the normal and a 1.3× font): no element past the right edge.

Platform support: latest Chrome on desktop and Android only (User's phone is Android; don't make changes for iOS/Safari). Mobile-first layout.

## Data model (initial sketch)

- `Trip` — id, name, startDate, endDate, countries, displayCurrency ("my money", BRL), currencies (each with its rate), baseCurrency (the main one, JPY), exchangeRate (= the main one's rate, for older data).
- `Day` — id, tripId, date, title, ordered placeIds.
- `Place` — id, tripId, dayId, googlePlaceId?, googleFetchedAt?, name, lat, lng, address?, notes (markdown), plannedTime, cost?. Later: category, tickets/checklist.
- `Leg` — id, tripId, fromPlaceId, toPlaceId, ordered `Segment[]`, source (`manual` | `google` | `navitime`), fetchedAt, alternatives (last suggestions), alternativesDate.
- `Segment` — id, mode (`walk` | `bus` | `train` | `subway` | `taxi` | `ferry` | `flight` | `other`), line/operator name, from/to stop names, from/to exits, times, path, distance, duration, fare, color, original (Japanese) names, notes.
- `Expense` — id, tripId, dayId? (absent = trip-wide), category (`lodging` | `transport` | `food` | `activities` | `shopping` | `other`), description, amount (Money), notes?.
- Backup: whole-trip JSON export/import (also the way to move data between PC and phone).

- **Phase 2 — Core planner** (done): trips, days, place search (Places API), pins on the map per day, reorder places, notes.

  - Places are added by Text Search (explicit Search button, never per keystroke), by tapping a Google POI on the map (details fetched only after "Add"), or as a free custom pin (no API call). Businesses (shops, restaurants) are tappable on both maps (Google's `clickableIcons`; the offline map names the pin after the OSM point of interest tapped). The tapped spot is marked on both maps with a "+" pin (`placePinSvg('+', { selected: true })`, `pending` prop of DayMap / OfflineMapPanel) while the card below the map asks to add it (User, 2026-10-31: no feedback before); Add or Cancel removes it.

- **Phase 3 — Legs** (done, including drawing manual segments on the map): segment editor between consecutive places (manual modes + suggested route), drawn on the map with a style per mode; walking segments routed via Google.
  - Any segment can be drawn by tapping points on the map ("Draw on map"). A drawing starts where the previous segment ends (or at the place) and ends where the next segment starts if that one is drawn; the last segment is never forced to the destination (a walk may stop at a bus stop): the draw toolbar has an "End at <destination>" checkbox (`Drawing.destination`). The automatic start is a checkbox too ("Start at <origin>" / "Start where the previous step ends", `Drawing.origin`; unticked, the first tap is the start), and a previous step ending at the destination (drawn when the end was still forced) is not used as the start. In reading mode each step has a quiet pencil and ✕ (edit / remove) at its top right; "Edit route" shows the full tools. Opening a leg's details (or drawing one of its segments) focuses both maps on it (`LegFocus`, built in `DayPage`): only that leg's line is shown and the map zooms to its two ends and every step's path; closing it shows the whole day again (fits refit only when a leg is opened/closed, not on every edit). While drawing, the segment being drawn is left out (its draft is shown). Rides (not walks) have a line color: the mode's default or one of 10 common line colors, no free picker (User's choice) (`LineColorPicker`, in the draw toolbar and the segment form; saved on `Segment.color`, used by the maps and the timeline badge). "Follow streets" snaps it with 1 Google Routes request: WALKING for walk, DRIVING for bus/taxi (at most 10 middle points, to stay on the Essentials SKU). Train/subway/ferry have no street geometry, so they stay as straight lines through the tapped points (free). Phase 5 export depends on segments having a path.
  - Legs are stored per (fromPlaceId, toPlaceId) pair (`src/db/legs.ts`), so they survive reordering; deleting a place deletes its legs.
  - "Suggest transit" = 1 NAVITIME request; all returned options are kept on the leg (`alternatives`), so switching option costs nothing. "Walking route" = 1 Google Routes request (whole leg A → B). A manual segment has no path until it is drawn; a leg with nothing drawable shows a thin dashed straight line.
  - NAVITIME `shapes` features come in route order tagged `ways: walk | transport`, color in `properties.inline.color`; they are matched to move sections in order (see `assignShapes`).
  - Suggestion time (leg editor, "Arrive by / Leave at" + time, `defaultTiming` in `LegItem.tsx`): arrive by the next place's planned time; else leave the previous place after its visit (planned time + visit minutes); else leave at 09:00. "Arrive by" = NAVITIME `goal_time` (Google `arrivalTime`). So a "From base" leg (base stops have no time) gives the hour to leave the hotel, shown on the base row ("From base Meander · Leave at 05:30", "Back to base Meander · Arrive at 21:10", from the leg's segment times, `legTimes`); leg summaries and other suggestions show "05:31–06:52".
  - Suggestions for dates more than 60 days ahead are requested for the next same weekday (`suggestionDate`): providers only know current lines/schedules, and NAVITIME times are estimates anyway.
  - Station exits ("B4口") are shown as "Exit B4" (`translateExit`).
  - Ride details read from NAVITIME (`navitimeProvider.ts`): train type (`transport.type` → `service`, "Local", "Special Rapid", "Nozomi 123"), headsign (`transport.destination` → "for Nishi-Umeda"), station numbers (`numbering` → `fromCode`/`toCode`, "Y15"), best car (`getoff` → `carHint`, "Cars 1–3"), stops on the way (`options=railway_calling_at` → `intermediateStops`; if the plan refuses it with a 400, the request is repeated without it once and never sent again, localStorage `tabi.navitime.callingAt`), platforms (`start_platform`/`goal_platform`, documented as timetable-contract only; read in case they come). Shown in the leg editor by `RouteTimeline` (design chosen by User from a mock, 2026-10-25, like Google Maps' transit steps): a row per station (time, English name, station-number tag in the line color, the Japanese name on its own line under it — `signName`/`lineSignName` drop operator prefixes, 〔〕 tags and train types —, "Enter by / Leave by Exit N", platform), and between them each ride (line badge in the line color, train type + "for <headsign>" with the Japanese after each, stops · time · fare · best car, folded "Stations on the way" with passed stations muted) or walk (dotted). Train to train with no walk between shows "Arrive 06:30 (JR-A31), change trains". Editing is hidden while reading: "Edit route" at the bottom shows small icon buttons under each step (Edit, Draw on map = `drawMap` icon, Move up/down, Remove) until "Done"; "Open in Google Maps", "Add step", "Clear route" and "Edit route"/"Done" sit in the leg's footer as small text links with icons ("Open in Google Maps" and "Edit route"/"Done" in `--accent-text`, "Add step" and "Clear route" muted, red on hover): one line on the PC, two on phones (link + Edit route, then Add step + Clear route). `rideFacts` (`src/format.ts`) is the plain-text version for exports. Leg header (User's mix of two mocks, 2026-10-25): "GETTING THERE" in red uppercase + "· 1 h 7 min · ¥1,080" muted, a chevron at the right to open/close; while closed, a one-line chain under it ("🚶4′ › Yotsubashi › 🚶6′ › JR Kyoto › Karasuma › 🚶14′": walks as a muted walker with minutes, rides as short badges in the line color, " Line" dropped); open, the chain hides (the timeline shows it all). A leg with no route shows a small dashed pill "+ Add the way there". The leg's controls are compact on every screen (32px tall on touch screens); the suggestion buttons read "Get a suggested route:" on its own line, then "[Car] [Public transport / Route by NAVITIME] [Walking] (i)", and below 480px the timeline puts the dots and line bars first, then the time (User's idea), so rides use almost the whole width. Explanations that would take a line of their own go behind an "i" (`InfoTip`, `info` icon): hover only with a mouse (no click, User's choice); on a phone, `@media (hover: none)`, a tap shows the text as a line under its row and another tap (or one elsewhere) hides it. On phones the base row reads "From base · Leave at 05:35" with the base's name muted on the line below. Verified on the Basic plan (2026-10-25): `railway_calling_at` is accepted; it lists every station passed, with a time only where the train stops (`stopsMade`). `transport.type` is the broad class (快速 for a 新快速), so the type glued to the line name wins. JR West codes come as "A47" and are shown "JR-A47" like its signs. Translation always starts from the kept originals, so rule changes also fix saved segments.
  - NAVITIME glues operators and train types to line names ("OsakaMetro四つ橋線", "京都市営烏丸線", "ＪＲ京都線新快速") and tags stations ("なんば〔Osaka Metro〕"): `translateLine` strips the type (→ `service`) and the operator prefix (longest known ending), `stationKey` drops 〔〕/()/【】; nicknames missing from Wikidata are in `LINE_ALIASES`, kana spellings in `STATION_ALIASES`. Stations are matched by the stop coordinates (`fromCoord`/`toCoord`), not the path ends. Saved legs are retranslated (no request) when their editor opens (`retranslateLeg`).
  - NAVITIME routes may include a flight (seen 2026-10-26, Osaka → Naha): its "line" is "空路 ([大阪]関西空港-[沖縄]那覇空港)". It becomes a `flight` segment (`moveToMode`, and `translateSegment` for saved legs via `isFlightLine`), named "Flight" (the 空路 kept as the original), from/to airports in English with their code from `AIRPORTS_JA` ("Kansai Airport (KIX)"). Its NAVITIME fare stays on the step (counted in the day) — unlike "Use my flight" steps.
  - Shape pieces are matched to sections by position too: a piece starting more than 500 m from where the section is belongs to a later one (short transfer walks often have no piece; before, they took the next walk's piece).
  - **Straight lines on the map (fixed 2026-10-31, User's report):** the matching took only the very next piece, so one piece that didn't fit (a big station's point more than 500 m from where its track starts: Osaka, Kyoto, Umeda) stopped it and every later step came out as a straight line (most legs saved from 26 Oct had 2-point rides). Now `assignShapes` looks up to 6 pieces ahead for the first one of the section's kind starting near it (walks 0.5 km, rides 1.5 km), skipping pieces nobody took. And a ride without a shape is drawn through its stops on the way (`drawnPath` in `src/mapLines.ts`, from `intermediateStops` coordinates, which saved NAVITIME rides have): both maps, the leg focus, the Logbook map and KML/GPX use it, so legs saved before the fix look right with no new request.
- **Phase 4 — Budget** (done): costs on places/segments/expenses, totals per day and trip, JPY ↔ BRL.
  - Every amount is a `Money` (amount + currency). Totals are kept per currency (`src/budget.ts`) and converted only for display: base-currency amounts × the trip's manual rate, display-currency amounts added as they are, other currencies shown apart (never guessed).
  - Walking per day (`dayWalking` in `src/db/legs.ts`): the walking steps of the legs along the day's route (base stops included) — distance, else drawn path length, else minutes at 4.5 km/h (shown with "≈"). Shown as "1.7 km on foot" on day cards and next to "N places" on the day page. Walks inside places aren't counted.
  - Day estimate = place costs not booked ahead + fares of the legs along its route (`dayMoney`); day expenses are money really spent (see "Budget page and the day's money"). Trip total ("Trip budget" on the itinerary page) = booked ahead + estimates.
  - A day with expenses is never removed when trip dates change (like a day with places).
  - Travelers: `Trip.travelers` (default 1; set on "New trip" and in Trip settings). Place costs are **per person** by default and count × the people going: `Place.people` overrides the trip's number for that place (e.g. 2 on the trip, 1 at a maid café; empty = follows the trip), `Place.costForGroup` = the price is for everyone. Restaurant/place/shop options have the same fields (`priceForGroup`, `people`; the form shows "In the budget: ¥1,500 × 2 = ¥3,000"; the options list shows only the total (the calculation on hover; its Price/Distance/Rating/Score/actions columns have fixed widths and are centered, so they line up across the separate group tables), and the comparison uses the per-person price, `pricePerPerson`); `addOptionToDay` copies them with the price, hours and book-ahead. `Place.kind` (place / restaurant / shop / other, like the options; editor "Kind") decides the budget category (`PLACE_KIND_CATEGORY`: activities / food / shopping / other) and what "book ahead" means (table vs ticket). Segment fares are per person × travelers, except taxis (per car). Booking a transport option prefills price × travelers; hotel prices are per room, never multiplied. Day expenses stay totals. Helpers in `src/budget.ts` (`travelersOf`, `peopleGoing`, `pricedTotal`, `placeCost`, `segmentCost`, `describePriced` → "¥1,000 × 2 = ¥2,000"). No schema change (unindexed fields).
  - Trip-wide expenses can be structured bookings (`src/components/BookingForms.tsx`): `Expense.hotel` (name, check-in/out or typed nights, optional price per night; `amount` is always the total, category lodging) and `Expense.flight` (from, to, date, time, flight number; category transport). The trip page groups them (Flights by departure, Lodging by check-in, Other) and shows "X of N nights in the itinerary · Y booked" (trip nights covered by dated stays).
